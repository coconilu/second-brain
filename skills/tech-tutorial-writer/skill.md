# 技术教程写作骨架

这个 skill 用来写"读者看完一遍就会用"的技术教程，不是 API 参考、不是设计文档。

## 核心心法

读者打开文章是**带着烦恼来的**，不是带着求知欲来的。所以：

1. **从痛点开**，不从概念开。第一段必须让读者认出"对，这就是我"。
2. **第一步必须能跑通**。在抽象之前，先给一个完整、最小、当场能复制粘贴的可运行例子。
3. **跑通之后才"回头看"**，把刚才发生的事抽象成一个**三元组心智模型**(类似"事件 × 过滤 × 动作")，用代码块把三层结构画出来。
4. **三个例子梯度递进**：例 1 最简单的正向用法，例 2 引入对比维度(如阻断 vs 不阻断)，例 3 展示另一个完全不同的事件/场景维度。
5. **每章用表格收束**，不要让读者读完一段还在脑子里整理多个变量。
6. **结尾给"速查"代码块**，让读者能直接收藏当 cheatsheet。

## 标准章节模板

按下面的顺序写。每节标题保持口语化，不要用"概述""背景"这种官腔。

### 1. 标题：`[主题]：从一个例子开始`

或者类似的"从…开始"句式。暗示读者：不会被一堆理论灌晕。

### 2. `## 一个真实的烦恼`

2~4 句话，描述读者每天会遇到的具体场景。**必须具体到可以想象画面**。
反例：「在开发中我们经常需要自动化某些任务」
正例：「你用 Claude Code 写 TypeScript，每次 Claude 改完文件，你都要手动跑一遍 `eslint --fix`。改三个文件就跑三次。烦了。」

然后一句话承诺：**"[本主题] 能解决这个问题：[一句话讲做什么]"**。

最后一句过渡："下面我们从零开始把这件事跑通"。

### 3. `## 第一步：[最小动作]` 和 `## 第二步：[让它生效]`

把跑通最小例子拆成两步左右(不超过三步)。每步：
- 给完整的命令/代码，路径写死，可以直接复制
- 代码块下面用 1~3 句解释关键行做了什么(不是逐行翻译)
- 如果有平台/依赖坑(jq、Windows、权限)，用 blockquote `>` 注明

最后一句过渡："搞定。…试试——[预期效果]"。

### 4. `## 回过头看：刚才发生了什么` (核心抽象节)

这是整篇文章的"顿悟点"。结构：
- 一句话："整个配置只有 N 层，对应 N 个问题"
- 一个**带箭头注释的代码块**，把刚才的配置/代码标注上每一层的语义：
  ```
  "PostToolUse"          ← 什么时候触发？
    "matcher": "Edit|Write"  ← 哪些工具调用？
      "type": "command"      ← 触发后干什么？
  ```
- 一句加粗收束："这就是 [主题] 的全部模型：**A × B × C**"

然后用 3 个 `### 子标题` 分别展开 A、B、C：
- 每个子节先一句话点出本质，再给一张表枚举常见取值
- 避免在这里塞例子细节，例子留给后面

### 5. `## [主题]的输入和输出` 或类似的接口节

讲数据契约。如何拿输入、如何返回结果。**用最小 JSON / 最小代码 + 一张表**。

### 6. `## 第二个例子：[引入对比维度的场景]`

通常引入一个**与例 1 形成关键对比**的场景，比如：
- 例 1 是 PostToolUse(事后)，例 2 就用 PreToolUse(事前)
- 例 1 是放行，例 2 就是阻断

例子讲完后，**一定要给一张对比表**，把两个例子的差异钉死。

### 7. `## 第三个例子：[拓宽维度的场景]`

展示这个工具/概念**还能用于完全不同的事**，证明它的通用性。例如 hooks 文章里第三例是 SessionStart，跟前两个 ToolUse 完全不同维度。

### 8. `## 配置放在哪` / `## 部署在哪`

讲文件位置、作用域、是否进 Git。一张表搞定。最后一句"经验法则"教读者怎么选。

### 9. `## 进阶：几个值得知道的细节`

3~5 个独立小节，每节一个 `###` 子标题，介绍一个进阶点。每节短 (3~6 句 + 必要时一个代码块)。**不要在这里教学**，只是"指个方向"，让读者知道"还有这个能力"。

### 10. `## 调试`

bullet list，4 条左右。给具体命令(`/xxx`、`--debug`)和最常踩的坑。

### 11. `## 速查`

一个代码块，把整篇文章的关键信息浓缩成 5~10 行。读者看完文章应该愿意复制这一段贴到自己的笔记里。

## 写作风格细则

- **句子短**。一句话讲一件事。多用句号，少用逗号串联。
- **第二人称"你"**，不要"我们"。读者是来解决自己问题的，不是来跟作者结伴的。
- **代码可复制**。所有路径、文件名、命令都给完整的，不要用 `<your-path>` 占位。
- **表格优先于列表**。当条目有 2 个以上属性(名称、含义、例子)时，必须用表格不用 bullet list。
- **加粗只用于"读者扫读时不能错过"的词**，一段最多 1~2 处。滥用加粗等于没加粗。
- **代码注释中文**，代码本身可以英文；标点中英文混排时英文符号后空一格(`Edit、Write`)。
- **章节末过渡句**: 每节最后一句要么收束本节("这就是…的全部"，要么自然带到下一节("下面我们…")。不要让读者从一段技术说明硬切到下一节标题。

## 常见反模式(出现就改)

- 第一段在讲历史背景或概念定义 → 删掉，从痛点开
- 没有跑通最小例子就开始讲机制 → 颠倒顺序
- 例子之间没有递进、互相平行 → 重新设计例 2 和例 3 的对比维度
- 表格只有两列(名称 + 描述) → 加一列"例子"或"典型用法"
- 进阶节写成了二级教程，每节又长又深 → 砍到指路深度
- 结尾写"总结" → 删掉，用速查代码块代替

## 使用流程

当用户要求按这个结构写文章时：

1. **先确认主题是否合适**：这个 skill 适合"工具/特性/机制"类教程(hooks、Git rebase、Docker volumes 这种)，**不适合**纯理论介绍、API 参考、设计决策记录。
2. **先问读者画像和痛点**(如果用户没说)：目标读者每天用什么、典型烦恼是什么。痛点不对，整篇就废了。
3. **先列出三个例子的递进设计**给用户确认，再动笔。例子选得好，文章就成了一半。
4. **写完先自检反模式清单**，再交付。
