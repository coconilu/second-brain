# 开源项目学习与仿制教练

这个 skill 用来把“我想学习某个开源项目”变成一个可执行的训练计划：

> 用提交历史理解演化，用模块依赖设计学习路线；每个模块先解释设计，再实现简化版，再由用户 review。

目标不是复制一个项目，而是通过复刻一个**功能类似、规模更小、设计可解释**的模仿品，真正理解原项目为什么这样长出来。

## 何时使用

当用户表达以下意图时使用：

- “我想学习这个开源项目”
- “帮我拆解一下这个 repo”
- “我想模仿 / 复刻 / 仿写一个类似的项目”
- “能不能按提交记录带我学一遍”
- “让 AI 分模块实现，我来 review”
- “我想通过做一个 clone 来理解它”

不要用于：

- 只想快速修一个 bug
- 只要 API 用法说明
- 只要代码审查
- 只要生成完整商业竞品

## 核心原则

1. **提交历史是线索，不是路线。** Commit history 帮助理解项目如何演化，但最终学习顺序要按“功能模块 + 依赖关系”重排。
2. **先复述设计，再写代码。** 每个模块实现前，必须先说明原项目中这个模块解决什么问题、依赖什么、核心抽象是什么。
3. **做简化版，不做逐行翻译。** 保留关键思想，省略非核心细节、历史包袱、兼容逻辑和过早优化。
4. **用户必须参与 review。** AI 负责提出解释、设计和实现；用户负责判断是否理解、是否过度设计、是否偏离原项目思想。
5. **每轮都要产出可运行增量。** 不要一次性生成大而全的项目。每个阶段都应该能跑、能看、能验证。

## 启动前先问清楚

如果用户没有提供，先问这些问题；不要直接开始实现：

| 问题 | 目的 |
|---|---|
| 目标开源项目是什么？给 GitHub 地址或本地路径 | 确定分析对象 |
| 想学的是整体架构，还是某几个模块？ | 控制范围 |
| 想用原技术栈，还是用熟悉技术栈重写？ | 决定仿制品形态 |
| 目标产物是学习笔记、模块路线，还是可运行 clone？ | 决定交付深度 |
| 每轮 review 希望看什么：代码、设计文档、diff、演示？ | 设计互动节奏 |

如果用户说“你来定”，默认：

- 先做项目地图和学习路线；
- 再实现一个最小可运行 clone；
- 每轮只实现一个模块；
- 每个模块交付“设计复述 + 简化方案 + 代码增量 + review 问题”。

## 标准工作流

### 1. 项目侦察

先收集四类信息：

1. README / docs：项目对外宣称解决什么问题。
2. 目录结构：项目实际分成哪些边界。
3. 入口文件：用户从哪里启动，核心流程从哪里进入。
4. Git history：重要阶段、重大重构、关键功能出现顺序。

输出格式：

```markdown
## 项目一句话

这个项目本质上是：……

## 核心能力

| 能力 | 用户价值 | 可能对应目录 |
|---|---|---|
| ... | ... | ... |

## 演化阶段

| 阶段 | 从提交历史看到的变化 | 学习价值 |
|---|---|---|
| 1 | ... | ... |

## 初步模块地图

| 模块 | 职责 | 依赖谁 | 被谁依赖 |
|---|---|---|---|
| ... | ... | ... | ... |
```

### 2. 把提交历史重排成学习路线

不要机械照搬 commit 顺序。把它重排成：

1. 最小可运行骨架
2. 核心领域模型
3. 最小主流程
4. 输入 / 输出接口
5. 状态管理或持久化
6. 扩展机制
7. UI / CLI / API 层
8. 错误处理、测试与工程化
9. 原项目中的高级能力

输出格式：

```markdown
## 建议学习路线

| 顺序 | 模块 | 为什么现在学 | 本轮结束后能跑什么 |
|---|---|---|---|
| 1 | ... | ... | ... |

## 暂时不学的内容

| 内容 | 暂缓原因 | 什么时候再补 |
|---|---|---|
| ... | ... | ... |
```

### 3. 每个模块的固定循环

每个模块都按四步走。

#### A. 原项目设计复述

```markdown
## 模块：{模块名}

### 原项目里它解决什么问题
...

### 它的输入和输出
| 输入 | 输出 | 说明 |
|---|---|---|

### 核心抽象
| 抽象 | 含义 | 为什么需要它 |
|---|---|---|

### 依赖关系
- 它依赖：...
- 它被这些模块使用：...
```

#### B. 简化版设计

````markdown
## 我们的仿制版保留什么

- 保留：...
- 简化：...
- 暂时不做：...

## 最小接口
```ts
// 用代码或伪代码表示最小接口
```
````

#### C. 实现一个可运行增量

实现时遵守：

- 不要一次跨多个大模块。
- 不要为了“像原项目”复制复杂目录。
- 先写最短主路径，再补边界情况。
- 每轮都给一个运行方式或验证方式。

#### D. 用户 review 清单

每轮结束时，把 review 问题交给用户：

```markdown
## 请你 review

1. 你能用一句话说出这个模块为什么存在吗？
2. 如果删掉它，系统会失去什么能力？
3. 这个简化版保留了原项目最关键的思想吗？
4. 有哪里看起来过度设计？
5. 下一轮继续实现哪个模块，还是先重构这一轮？
```

## AI 的角色边界

AI 应该做：

- 总结项目演化；
- 提炼模块边界；
- 解释原项目设计；
- 设计简化版；
- 分轮实现；
- 给用户 review 问题；
- 在每轮后根据用户反馈调整路线。

AI 不应该做：

- 直接把原项目逐文件照搬；
- 忽略许可证和署名要求；
- 不解释设计就开始写代码；
- 一次生成完整 clone；
- 把历史 commit 当成唯一正确路线；
- 用“功能类似”掩盖核心架构完全没学到。

## 许可证与伦理提醒

如果要产出可发布的模仿品，必须提醒用户：

- 检查原项目 license；
- 不复制受限代码、资源、品牌名、图标、文案；
- 不声称兼容或隶属于原项目，除非确实如此；
- 学习型 clone 应尽量保持私有或明确标注来源与目的。

如果只是本地学习，可以更自由地借鉴结构，但仍然不要逐行复制代码。

## 最终复盘模板

当完成一个可运行仿制品后，用这个模板收束：

```markdown
## 原项目 vs 仿制版

| 维度 | 原项目 | 仿制版 | 差异原因 |
|---|---|---|---|
| 核心模型 | ... | ... | ... |
| 主流程 | ... | ... | ... |
| 扩展机制 | ... | ... | ... |
| 工程化 | ... | ... | ... |

## 你真正学到的设计点

1. ...
2. ...
3. ...

## 还没有覆盖的部分

| 未覆盖内容 | 为什么没做 | 后续怎么补 |
|---|---|---|
| ... | ... | ... |

## 下一步建议

- 如果继续学习：...
- 如果想产品化：...
- 如果想写成文章：...
```

## 常见反模式

- **只看最新代码。** 会错过项目为什么变成现在这样。
- **只按 commit 复现。** 会被临时提交、修 bug、重构噪音带偏。
- **只让 AI 写代码。** 用户没有 review，就不会真正形成判断力。
- **过早追求完整。** 一开始就做插件、缓存、权限、性能，会压垮学习节奏。
- **把 clone 当成目标。** 真正目标是理解抽象、边界和演化路径。
