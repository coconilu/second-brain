## 何时使用

当审查 AI 生成代码的可复用性问题时加载此 skill——尤其是 post-generate-reviewer 和 component-scanner 代理。

## 可复用性标准

当生成代码满足以下条件时，应被视为"可能与已有功能重复"：

### 1. 导出的函数/类
检查生成代码定义的函数或类是否与目录中已有导出功能重叠。比较完整签名（参数类型、返回类型）——不仅是名称。

### 2. React / Vue / Svelte / Angular 组件
检查生成的组件是否与目录中已有组件的用途相似（名称、props、行为）。

### 3. 自定义 Hook / Composable（useXxx 模式）
任何生成的 `use*` 函数都应与目录中已有 hooks 进行比较。Hooks 天然具有高度可复用性。同时检测 Vue composables 和 Angular services。

### 4. 工具/辅助函数
生成代码中的纯函数（无副作用、确定性输出）应与已有工具函数对比。常见示例：日期格式化、字符串处理、数据转换、数字格式化。

### 5. API / 数据请求
任何 fetch/axios/query/graphql 调用都应与目录中的 API 客户端条目比对。在组件中直接写 fetch 调用是强烈的重复信号。

### 6. 类型/接口定义
生成的类型定义与目录中已有类型重复时，应标记为建议导入复用。

### 7. 常量/配置
生成的常量与已有配置值或常量导出重复时，应标记。

## 判断启发式

将生成代码与目录对比时，考虑以下维度：

- **签名相似度**（最强信号）：相同参数名、相同参数类型、相同返回类型 → Critical。部分类型重叠 → High。
- **名称相似度**：相似的函数/组件名称（编辑距离、词重叠、语义含义）→ 可能匹配。例如：`getUserById` 与 `fetchUser`——不同名称，相同签名 → High。
- **行为意图**：相同领域概念（如"格式化日期"、"验证邮箱"、"发起 API 请求"）→ 可能匹配，即使签名略有不同。
- **导入上下文**：如果生成代码引入了与已有组件相同的第三方依赖 → 可能相关功能。
- **依赖中心度**：优先复用 Hot 层级的项目（被多个文件/核心模块导入）而非 Low 层级的项目——Hot 层级的项目是"权威"实现。

## 增强启发式（社区最佳实践）

参考 Aider、Cursor、Continue.dev、Tabby 等开源工具的设计理念，以下额外维度可进一步提升判断精度：

- **PageRank 加权中心度**（受 Aider 启发）：不仅统计被几个文件导入，还考虑导入者的"权重"。被 auth/routing/state/config 等基础设施模块导入的组件权重 ×3。被 feature page 导入权重 ×1。被 test 文件导入权重 ×0.5。综合加权分 = 基础设施导入数 ×3 + 普通导入数 ×1 + 测试导入数 ×0.5。
- **代码修改热度**（git churn 分析）：使用 `git log --follow --oneline <文件路径> | wc -l` 统计文件历史提交次数。被频繁修改（>10 次）的组件升级一档：如果重复实现它，未来需要维护两份逻辑同步更新，危害更大。
- **测试覆盖度信号**：有对应测试文件（`*.test.*` / `*.spec.*`）的组件行为明确、经过验证 → 比无测试的组件更值得复用。有测试的组件权重 ×1.5。
- **语义近似度**（受 Cursor 多策略检索启发）：不仅比较名称和签名，还比较：所在目录结构（如都在 `src/auth/` 下）、第三方依赖导入（都用了 `jsonwebtoken`）、JSDoc/注释中的自然语言描述。生成代码与目录条目的文件路径越接近、依赖越相似，越可能实现相同功能。
- **近似重复检测**（受 jscpd 启发）：除了对照已有导出条目，还要识别项目中"应该提取但尚未提取"的重复模式。使用 `rg` 搜索生成代码中的关键逻辑片段（如一段特有的条件判断、算法公式）是否在项目中其他地方出现——即使对方没有导出。此类发现建议先提取为共享模块，再统一复用。

## 严重等级（含多维度加权）

| 等级 | 条件 | 操作 |
|-------|-----------|--------|
| **Critical** | 完全重复——相同名称、相同签名、相同行为；或签名完全相同且目标组件为 Hot 层级 + 高修改热度（>10 次 git 提交） | 替换为 import，删除重复代码 |
| **High** | 高度相似——名称略有不同，签名和行为相同；或行为意图相同且 PageRank 加权分 >10 | 重构为使用已有实现，可能需要小幅适配 |
| **Medium** | 部分重叠——部分功能共享，签名不同；或检测到未提取的近似重复（散落在 2+ 个文件中的相似逻辑） | 提取共享部分，保留独有部分；建议提取为共享模块 |
| **Low** | 潜在可复用——同一领域，实现不同；或目标组件 Low 层级且无测试覆盖 | 添加注释标记，暂不处理 |

## 审查输出格式

报告发现时，使用以下格式：

```markdown
## Review: {filename}

### Critical
- **Line {N}**: `{生成的代码}` 与已有 `{目录条目}` 重复，位于 {file}:{line}。**已替换为 import。**

### High
- **Line {N}**: `{生成的代码}` 与已有 `{目录条目}` 高度相似，位于 {file}:{line}。名称不同，签名相同。**已重构。**

### Medium
- **Line {N}**: 与 `{目录条目}` 部分重叠，位于 {file}:{line}。**已提取共享逻辑。**

### Low
- **Line {N}**: 可考虑复用 `{目录条目}`，位于 {file}:{line}。后续重构时关注。
```
